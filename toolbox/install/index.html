Installing Helix Toolbox

Every release on the releases page has the same tested build for Linux on x86_64 and on aarch64 (ARM64), each in four forms: an Arch package, a Debian/Ubuntu package, an RPM package for Fedora and openSUSE, and the bare program, and the window beside them (below). With Rust installed, cargo install builds it on your machine instead (below). It needs glibc 2.35 or newer (Debian 12, Ubuntu 22.04, Fedora 36, current Arch and openSUSE Tumbleweed, or later).

A package

Section titled “A package”

A package puts helix-toolbox in /usr/bin, with shell completions for bash, zsh and fish, manual pages (man helix-toolbox), and a menu entry, Helix Toolbox (Terminal), that opens it in a terminal. Your package manager then knows it and removes it cleanly. Download the file for your distribution from the release, check it (below), then:

On ARM64 (a Raspberry Pi 4 or 5 with a 64-bit system, an Apple Silicon Mac with Fedora Asahi Remix, an ARM laptop or server):

Entries for programs built only for x86_64, such as Steam, Google Chrome, DaVinci Resolve and the CachyOS and Chaotic-AUR repositories, are not shown on ARM64.

The packages are not signed with a distribution key; zypper needs --allow-unsigned-rpm to accept that. Check the file first instead (below).

A newer release is installed the same way, over the old one, or from inside Helix Toolbox: the Helix Toolbox row of the Updates screen downloads it, checks it and installs it for you (helix-toolbox updates --online --apply helix-toolbox), the window’s package with it when that is installed. On Arch, the repository below does away with the downloads. Remove it with sudo pacman -R helix-toolbox, sudo apt remove helix-toolbox, sudo dnf remove helix-toolbox or sudo zypper remove helix-toolbox; your settings, profiles and history in ~/.config/helix-toolbox and ~/.local/state/helix-toolbox stay.

The Arch repository

Section titled “The Arch repository”

Arch and its derivatives can take both packages from a pacman repository instead, which every release rebuilds on GitHub Pages. Then pacman -Syu, garuda-update or whatever updates the system updates Helix Toolbox and its window too, and the Updates screen’s Helix Toolbox row runs that. Then:

The repository carries x86_64 and aarch64 packages and only the latest release. Its packages are the release’s own files, so the checksums and build attestations on the release page apply to them; the repository itself is not signed, which the SigLevel line tells pacman. A package installed from a downloaded file is taken over by the repository at its next version.

The window

Section titled “The window”

helix-toolbox-gui opens the same catalog in a window (GUI.md). Each release has it for x86_64 and aarch64 as an Arch package, a Debian package, an RPM and an AppImage. Install the helix-toolbox package above first: the window runs the command line for the built-in steps, and the packages require it.

The Updates screen’s Helix Toolbox row updates the window’s package with the command line’s, and replaces an AppImage in place.

The packages add a menu entry, Helix Toolbox, beside the command line’s Helix Toolbox (Terminal). The window is drawn by WebKitGTK 4.1, which the Debian and RPM packages install with it; the AppImage carries its libraries. It is not on crates.io: building it needs the frontend, as GUI.md describes.

Without installing

Section titled “Without installing”

start.sh in this repository downloads the latest release’s program, checks it against the release’s SHA256SUMS, and runs it, without installing anything:

From a checkout with Rust installed, ./start.sh builds and runs the source instead. Piped to sh, it always downloads the release: it builds only when it runs as the start.sh file of a Helix Toolbox checkout, never whatever Cargo project the current folder holds.

Checking a download

Section titled “Checking a download”

Each release lists the SHA-256 sum of every file in SHA256SUMS:

That shows the file arrived as published. To check where it was built, each file also carries a signed build provenance attestation from GitHub Actions: which repository, workflow and commit produced it. With the GitHub command line:

It succeeds only for a file built by this repository’s release workflow, and says which workflow run built it.

What each build is made of is in the release’s software bills of materials, CycloneDX JSON from the lock files it was built from: helix-toolbox-sbom.cdx.json (every crate in the program), helix-toolbox-gui-sbom.cdx.json (the window’s crates) and helix-toolbox-gui-frontend-sbom.cdx.json (its frontend packages). They are in SHA256SUMS and attested like the programs, and any scanner that reads CycloneDX can check them against vulnerability databases.

With Cargo

Section titled “With Cargo”

With Rust 1.89 or newer (rustup), Cargo builds Helix Toolbox on your machine and puts it in ~/.cargo/bin, with htb beside it:

That takes the latest release from crates.io. Straight from GitHub instead, a release by its tag or the newest code:

cargo install again updates it (the Updates screen’s Helix Toolbox row runs it for you), and cargo install-update -a from the cargo-update crate updates every program installed this way; Cargo never updates anything by itself. cargo uninstall helix-toolbox removes it. A copy built this way has no manual pages or menu entry (the packages have those); helix-toolbox completions bash|zsh|fish prints its shell completions. A build from GitHub reports the version in Cargo.toml, which can be a patch behind the tag it was built from; the crates.io and release builds report the release’s own.

Coming from HelixForge

Section titled “Coming from HelixForge”

HelixForge is Helix Toolbox from 1.7. A HelixForge package updates to the helix-toolbox package from the Updates screen, or by installing the new package as above: it replaces helixforge and keeps a helixforge command that runs Helix Toolbox. A Cargo install moves with cargo install --locked helix-toolbox (then cargo uninstall helixforge). Settings, profiles and history move to their new folders by themselves the first time it starts; MIGRATION.md lists what changed.
